# 여러 에이전트 작업 설계안 v2 (2026-10-08)

상태: 민재님 승인(2026-10-08 12:18 KST), G8에서 반영.
v1(02:42 UTC)에서 바뀐 점: "동시에 많이"가 아니라 **호출 수, 입력 크기, 다시 하는 범위를 줄이는 것**이 중심이다. 근거는 Codex G6 검토(`팁스\output\review-pipeline-g6-review-2026-10-08\G6_REVIEW_AND_WORKFLOW.md`)와 v1의 시간 기록이다.

## 1. 바뀌는 작업 흐름 (단계 하나)

1. **다시 할 단계 고르기 (스크립트)**: 단계마다 입력 파일 해시를 지난 실행과 비교한다. 바뀐 단계와 그 뒤 단계만 다시 한다. 바뀌지 않은 단계는 건너뛰고 그 문서도 다시 읽지 않는다.
2. **작업 묶음 만들기 (스크립트)**: 작업자마다 입력 파일 하나를 만든다. 넣는 것은 목적 한 줄, 그 작업에 필요한 승인 기준 원문 필드(요약하지 않고 그대로 복사), 대상 리뷰 원문, 출력 경로, 통과해야 할 검사, 상한이다. 에이전트는 이 파일만 읽는다. 전체 스키마, 02_reviews.csv 전체, CLAUDE.md 상세는 읽지 않는다.
3. **작업자 배정**: 역할 수와 호출 수를 분리한다. 묶음마다 새 에이전트를 부르지 않고, 작업자 하나에 묶음 목록을 주어 차례로 처리하게 한다(한 번의 호출에 묶음 여러 개).
4. **실행 순서**: 같은 정의와 같은 모델의 작업자 중 하나를 먼저 띄우고, 첫 출력이 나오면 나머지를 띄운다(캐시 후보, **절감률 미확인**). 사람 확인이 필요한 관문은 큰 묶음 앞에 둔다.
5. **기계 검사 (스크립트)**: 형식, 인용, 숫자를 검사한다. 실패한 묶음만 다시 보낸다.
6. **독립 감사**: 작성자와 다른 감사자 하나를 쓴다. 기계 검사를 통과한 결과의 표본과 **바뀐 행 전부**(추가, 삭제, 인용 변경)를 본다. 작성자 대화는 넘기지 않는다. 표본이 비면 PASS가 아니라 따로 판정한다.
7. **기록**: 단계마다 호출 수, 동시 수, 재시도, 입력과 출력 크기, 시간을 한 줄로 남긴다. 상한에 닿으면 자동 추가 호출을 멈추고 보고한다.

**상한 (기본값)**: "빨리"라는 말로 올리지 않는다. 바꾸려면 민재님이 숫자를 직접 적어 지시해야 한다.

| 항목 | 기본값 | 비고 |
|---|---|---|
| 대량 작업자(sonnet) 동시 실행 | 태깅 8, 이슈 라벨과 설계 정보 추출 4 | Codex 안은 2. 태깅은 2026-10-09 민재님 지시로 8 |

## 3. 효과를 확인할 비교 방법

- **대상**: 이미 끝난 G6 3부 재판정(6묶음, 리뷰 276개, 2항목)을 같은 입력으로 다시 돌린다. 결과가 좋으면 태깅 묶음 일부로 넓힌다.
- **비교 대상**: A 지금 방식(묶음마다 새 에이전트), B v2 동시 2, C v2 동시 4. 캐시 먼저 띄우기는 C에서 켜고 끈 두 번으로만 본다.
- **잴 것**: 벽시계 시간(timing.jsonl), 헤드리스 결과의 사용량(입력, 캐시 쓰기, 캐시 읽기, 출력 토큰과 total_cost_usd), 에이전트 호출 수, Read 호출 수와 같은 파일 반복 읽기, 재시도 수.
- **품질 조건**: 기계 검사 PASS가 같아야 한다. 재판정 값이 지금 결과와 일치하는지와 감사 FAIL 비율이 기존 이하인지도 본다. 품질이 같고 시간과 사용량이 둘 다 나빠지지 않을 때만 채택한다.
- **주의**: total_cost_usd는 Max 요금제라 실제 청구가 아니고 API 환산값이다. 비교에는 상대값만 쓴다. 문서 글자 수 절감(18,901자 → 2,620자)을 비용 절감률로 바꿔 말하지 않는다.
- 비교도 실행이므로 돌리기 전에 규모를 한 줄로 알리고 민재님 답을 받는다.

## 부록 A. 근거와 v1 정정

- [확인] G6 재판정 2항목을 처리한 하위 에이전트들이 13_detail_schema_approved.yaml(18,901자)을 11번, 묶음 계획을 9번, 02_reviews.csv 전체를 6번 읽었다(`g6_subagent_reads.json`). 필요한 두 항목만 고르면 2,620자다(Codex). 파일 글자 수는 PC에서 다시 재서 일치했다.
- [확인] v1 시간 기록: 태깅 28묶음은 에이전트 시간 합 63.4분이 18.8분에, G6 3부는 6개를 차례로 돌려 6.9분이 걸렸다.
- **v1 정정 1**: v1은 "묶음 작업은 자기 몫만 읽어 공유 브리프 효과가 작다"고 했는데 틀렸다. 묶음 에이전트도 전체 스키마를 매번 읽었다. 공유 브리프만으로는 부족하고, 작업에 필요한 기준만 담은 입력 파일이 필요하다.
- **v1 정정 2**: v1은 "동시 실행은 사용량이 그대로"라고 했다. 순서만 바꾸면 맞지만, 호출마다 지시문과 스키마를 읽는 고정 비용이 붙으므로 사용량은 호출 수가 정한다. 그래서 작업자 재사용으로 호출 수를 줄인다.
- **v1 정정 3**: v1의 상한(sonnet 10, 상위 모델 4)은 위 상한 표로 바꾼다.

## 부록 B. 캐시 먼저 띄우기와 작업자 재사용 함께 쓰기

- **작업자 안**: 같은 작업자가 다음 묶음을 처리할 때는 앞 묶음까지의 맥락을 캐시에서 싸게 다시 읽는다. 재사용과 캐시는 여기서 자연스럽게 같이 간다. 다만 맥락이 계속 길어지므로 작업자당 4묶음 또는 200개로 끊는다.
- **작업자 사이**: 먼저 띄우기로 나눠 쓸 수 있는 것은 같은 에이전트 정의와 도구 설명 부분뿐이다(추정). 입력 파일은 프롬프트 뒤에 읽으므로 작업자끼리 나눠 쓰지 못한다. 그래서 효과는 작을 수 있고, **절감률은 확인되지 않았다**.
- **모델**: 캐시는 모델마다 따로다. 대량 작업자는 모두 sonnet으로 맞추고 섞지 않는다.
- **대기**: 캐시는 5분 동안 요청이 없으면 만료된다. 사람 관문은 큰 묶음 바로 앞이 아니라 그 전에 끝낸다.
- 작업자 재사용은 "한 번의 호출에 묶음 목록"으로 한다. 끝난 에이전트에 이어 말 걸기는 PC Claude Code 버전에 따라 다를 수 있어 쓰지 않는다(버전 미확인).
