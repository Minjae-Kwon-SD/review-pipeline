# 설명서: 리뷰 분석 파이프라인은 어떻게 짜여 있고, 어떻게 시키는가

검토자께 드리는 설명이다. 결과물은 `runs/perfume-db-2026-10-07/`의 HTML 두 개(리뷰 리포트 한국어판, 개발 가이드 한국어판)이고(영어판은 제출 전 요청이 있을 때 한국어 최신판으로 다시 만듦), 실행 방법과 표는 저장소 맨 위 [README.md](../README.md)에 있다. 이 문서의 숫자는 `python scripts/doc_facts.py build`가 회차 파일에서 모은 값이고 출처는 [doc_facts.md](doc_facts.md)에 있다.

## 1. 왜 이 구조인가

### 단계마다 파일을 남긴다

모든 단계는 입력 파일을 읽고 출력 파일 하나(또는 정해진 묶음)를 쓴다. 누가 어떤 파일을 쓰는지는 `CLAUDE.md`의 파일 계약 표에 있다.

- **중간에 끊겨도 이어서 돈다.** 단계 상태는 `state.json`에 남고, 다시 부르면 done이 아닌 첫 단계부터 시작한다.
- **한 단계만 다시 돌릴 수 있다.** 예를 들어 리포트 문장만 고치면 태깅부터 다시 하지 않고 8단계부터 돌린다. HTML은 모델 없이 몇 초면 다시 만든다.
- **틀린 곳을 파일로 짚을 수 있다.** 태그 하나, 숫자 하나가 어느 파일 어느 줄에서 왔는지 따라갈 수 있다. 감사관도 이 파일들을 읽어 판정한다.
- **모델의 기억에 기대지 않는다.** 에이전트끼리 대화로 넘기지 않고 파일 경로로만 넘긴다. 에이전트는 자기 출력 파일만 쓴다.

### 사람 관문을 둔 이유

모델이 정하면 안 되는 것, 정하면 뒤가 전부 바뀌는 것만 사람이 정한다.

| 관문 | 왜 사람이 정하나 |
|---|---|
| ASIN 확인 | 무엇을 분석할지가 결론의 대표성을 정한다 |
| 스키마(주제) 승인 | 모든 태그와 집계의 기준이다. 나중에 바꾸면 태깅부터 다시 해야 한다 |
| 정답 세트 태깅 | 태거를 채점할 기준이라 모델이 만들면 자기 채점이 된다. 태거 결과를 보기 전에 한다 |
| 세부 이슈 라벨 승인 | "금방 날아감"처럼 리포트에 그대로 나오는 이름과 경계를 정한다 |
| 설계 정보 항목 승인 | 개발 가이드가 무엇을 재료로 쓸지 정한다 |

나머지 작은 선택(표기 방식, 제외 낱말, 검사 규칙 등)은 Claude가 정하고 보고의 "정한 것"과 `docs/decisions_log.md`에 남긴다. 돈이 드는 호출과 밖으로 나가는 일은 사람이 정한다.

### 스크립트와 모델의 역할을 나눈 이유

- **숫자는 스크립트만 만든다.** 별점 보정 가중, 비율, 격차, 개수는 `weight.py`, `issues.py`, `guide_metrics.py`가 계산해 JSON에 넣는다. 모델이 숫자를 계산하면 틀려도 알아채기 어렵다.
- **모델은 판단과 문장만 한다.** 리뷰의 뜻 읽기(태깅, 추출), 범주 찾기(스키마, 세부 이슈 초안), 해석 문장 쓰기, 원문 대조 판정.
- **문장 속 숫자도 기계로 대조한다.** `audit_quotes.py report`와 `guide_check.py`가 문장의 숫자를 metrics 값과, 인용을 리뷰 원문과 글자 그대로 맞춰 본다. HTML 검사는 화면 숫자 1053개(리뷰 리포트)와 312개(가이드)를 JSON과 대조한다.
- **만드는 쪽과 판정하는 쪽을 나눈다.** evidence-auditor는 읽기 도구만 갖고, 판정 YAML만 돌려준다. 고치는 일은 그 파일을 만든 에이전트가 다시 한다.

## 2. 에이전트마다

| 에이전트 | 왜 따로 뒀나 | 무엇을 보나 | 무엇을 못 하나 |
|---|---|---|---|
| asin-selector | 상품 고르기는 처음 한 번, 사람 확인 전에만 | 후보 표(`00_candidates.csv`), 카테고리 설정 | 리뷰 수집, 별점 분포 고치기 |
| schema-drafter | 스키마는 모든 것의 기준이라 상위 모델이 따로 깊게 | 스키마 표본(정답 세트 제외), 공통 주제 | 정답 세트 보기, 승인본 고치기 |
| review-tagger | 양이 많아 묶음마다 동시에, 빠른 모델로 | 자기 묶음 리뷰, 승인 스키마 | 다른 묶음, 스키마 고치기, 숫자 |
| issue-labeler | 주제마다 따로 불러 하위 범주를 깊게 | 주제 하나의 표본 인용 | 라벨 붙이기(승인 뒤 일), 태그 고치기 |
| issue-tagger | 라벨 붙이기는 양이 많아 동시에 | 묶음 하나의 인용, 승인 라벨 정의 | 목록 고치기, 주제와 감성 고치기 |
| report-writer | 해석 문장은 숫자와 분리해 한 곳에서 | `05_metrics.json`, `05_tables.md`, 태그 인용 | 숫자 계산, 태깅, 판정 |
| evidence-auditor | 만든 쪽과 판정하는 쪽을 나누려고 | 원문 리뷰, 승인 스키마와 라벨 정의, metrics, 대상 파일 | 파일 쓰기(도구가 Read, Grep, Glob뿐), 기준값 바꾸기 |
| detail-schema-drafter | 가이드용 "설계 정보"는 주제 태그와 다른 질문이라 | 설계 정보 표본(정답 세트 제외) | 전체 추출, 태깅 |
| detail-extractor | 리뷰마다 값 뽑기는 양이 많아 동시에 | 자기 묶음 리뷰, 승인 항목 | 항목 고치기, 집계 |
| benchmark-researcher | 웹을 보는 유일한 에이전트라 권한을 여기만 | 공개 웹(아마존 사이트는 열지 않음) | 리뷰 읽기, 숫자 계산, 가이드 문장 |
| guide-writer | 가이드 문장은 리포트와 질문이 달라 | `16_guide_metrics.json`, 출처가 확인된 웹 주장만 | 웹 조사, 숫자 계산 |
| report-translator | 번역은 내용을 바꾸지 않는 일이라 쓰기와 분리 | 감사를 통과한 한국어 문장, 이름표, 인용 원문 | 내용 더하기와 빼기, 숫자 바꾸기 |

에이전트 지시문에는 카테고리 이야기가 없다. 향수에 관한 것은 `config/categories/perfume.yaml`과 승인된 파일에만 있다.

## 3. 어떻게 시키는가

### 새 카테고리 시작

1. `config/categories/<카테고리>.yaml`을 쓴다(검색어, 상품 제목 규칙, 가이드 설정). 향수 파일을 본뜬다.
2. Claude Code를 상위 모델로 열고 부른다.

```text
/review-run perfume-db 2026-10-07
```

3. 메인 세션이 단계를 돌리다 관문에서 멈추고, 무엇을 봐야 하는지 알린다.

### 관문에서 사람이 하는 말

이번 회차에서 실제로 쓴 말이다.

- ASIN: 후보 표를 보고 카드에서 고름(바디 미스트와 한 브랜드를 빼고 상품 6개).
- 스키마: 초안을 보고 승인(고칠 곳이 있으면 말하고 Claude가 고친 판을 다시 확인).
- 정답 세트: 태깅 화면에서 리뷰를 하나씩 태깅. 애매한 경우는 대화로 규칙을 정함(예: 시점 없는 누출은 배송, 전체 만족도는 내용 기준). 이 규칙이 룰북에 들어간다.
- 세부 이슈 라벨: 카드에서 "제안 반영 후 승인".
- 설계 정보 항목: 두 곳을 고치라고 한 뒤 "승인".
- 그 밖: 개발 가이드는 "지금 데이터로"(유료 호출 없이), 요구사항 확인에 "맞아", 작은 선택은 "선택 나오는거 웬만하면 그냥 너가해봐".

### 실제로 쓴 지시(브리프) 예

메인 세션이 헤드리스 실행에 넘긴 지시는 단계 이름, 부를 명령, 부를 에이전트, 실패하면 할 일을 순서대로 적는다. 가이드 머리 숫자를 고칠 때 쓴 지시의 앞부분이다.

```text
회차 perfume-db-2026-10-07의 개발 가이드 머리 숫자 5번 손질만 한다. ...
1. python scripts/timing_report.py mark perfume-db-2026-10-07 start 20b_head_text --kind agents
2. guide-writer를 부른다(모델 따로 주지 않음). ... 다른 문장은 한 글자도 바꾸지 않는다. 숫자는 [m:키]로만.
3. python scripts/guide_check.py perfume-db-2026-10-07. FAIL이면 오류를 붙여 guide-writer를 한 번 더 부른다.
4. python scripts/guide_diff.py perfume-db-2026-10-07 17_guide_v3.md 17_guide.md
```

헤드리스 실행은 권한을 넓히지 않고 허용 도구만 준다(스크립트 실행과 `runs/` 쓰기). 정답 세트 폴더는 읽기를 막는다.

### 다시 돌리기

- 끊긴 회차: 같은 명령으로 다시 부르면 `state.json`에서 done이 아닌 첫 단계부터 이어서 한다.
- 한 단계만: 그 단계의 스크립트나 에이전트만 다시 부른다. 예: 리포트 문장을 고친 뒤 `python scripts/render_html.py build perfume-db-2026-10-07`와 `check`.
- 다른 언어판: `python scripts/render_html.py build perfume-db-2026-10-07 --lang en`(번역 문장 `06_report_en.md`와 이름표가 있어야 함).
- 숫자 정의를 바꿀 때: 설정이나 스크립트를 고치고 metrics를 다시 만든 뒤, 바뀐 문장만 고치고(`guide_diff.py`로 바뀐 줄을 뽑아) 그 줄만 다시 감사한다.

## 5. 시간

기록(`timing.jsonl`, `costs.jsonl`)에서 모은 값이다. 사람 대기는 기계 시간에서 뺐다.

| 영역 | 첫 실행 | 다시 실행 어림 | 사람 시간 |
|---|---|---|---|
| 리뷰 리포트 | 113.9분 | 63.7분 | 206.7분 |
| 개발 가이드 | 81.3분 | 74.9분 | 21.4분 |
| 영어판과 보강(G3 이후) | 173.5분 | 63.6분 | 0.0분 |
| 합 | 368.7분 | 202.2분 | 228.1분 |

- **첫 실행**은 이번에 실제로 쓴 기계 시간이다. 코드와 지시를 고쳐 가며 다시 돌린 시도가 모두 들어 있다.
- **다시 실행 어림**은 단계마다 마지막 성공 1회만 더하고, 이번에 고치느라 생긴 단계(리포트 손질, 가이드 고치기, 머리 숫자 다시 계산, 사양 정리, 문장 흔들림 고치기)를 뺀 값이다. 지금 코드와 지시로 같은 회차를 처음부터 돌리면 이 정도로 본다.
- **사람 시간**은 관문에서 기다린 시간이다. 대부분이 정답 세트 태깅(178.5분)이고, 규칙을 대화로 함께 정한 첫 회차라 길었다. 다음 카테고리에서는 룰북이 있어 짧아질 것으로 본다. 기다린 시간이라 실제로 화면을 본 시간보다 길 수 있다.
- 비용은 API 요금 환산 어림값(Claude Max 구독, 실제 결제 없음)으로 헤드리스 실행 33번에 $145.63이다(리뷰 리포트 $70.42, 개발 가이드 $28.31, 영어판과 보강(G3 이후) $46.90). 대화 세션에서 직접 한 일은 기록이 없어 빠져 있다.

## 6. 다음에 할 것

- **정답 세트를 둘로 나눈다.** 규칙을 만드는 리뷰와 채점하는 리뷰를 나눠 표본 밖 정확도를 잰다. 지금의 F1 0.96은 같은 리뷰로 규칙을 다듬은 뒤 잰 값이다.
- **ASIN 고르는 기준을 매출이나 검색 순위로.** 유료 수집을 켤지 정할 때 함께 정한다.
- **상품 사양 더 모으기.** 이번에 모은 농도, 노트, 성분에 더해 병과 분사기 사양, 용량별 가격을 같은 출처 기준으로 채운다. 상품 수가 늘어야 사양과 불만을 비교할 수 있다.
- **개발 가이드 영어판.** 가이드 숫자 표기의 번역 규칙과 화면 문구 파일을 만든 뒤 리뷰 리포트와 같은 방식으로.
- **두 번째 카테고리(예: 제모)로 한 번 더.** 설정 파일 하나로 도는지, 관문 시간이 얼마나 줄어드는지 본다.
- **카테고리와 무관한 리뷰 빼기.** 이번에 섞인 무관한 리뷰를 다음 실행부터 태거가 off_category로 표시해 집계에서 뺀다(규칙은 이미 넣음).
